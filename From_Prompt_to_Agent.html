02 / WHY AGENT

从“回答问题”到“完成任务”

Agent 的核心不是“用了 LLM”，而是能围绕目标观察、决策、行动、验证，并把任务推进到完成。

概念统一
Chat

回答一次

对当前问题生成答案，不承诺执行后续步骤。

例：“AUM 是什么？”回答定义后结束。
Copilot

人主导、AI 辅助

人决定下一步，AI 在当前界面里建议或代写。

例：分析师选好表，Copilot 帮忙写 SQL。
Workflow

固定步骤自动跑

预设 A→B→C，异常分支通常靠规则处理。

例：每天 9 点刷新数据并发送固定 PDF。
Agent

围绕目标动态推进

根据结果选择工具和下一步，同时保留边界与验证。

例：发现 AUM 异常后，自动选择客户、产品、渠道维度下钻，并引用证据。
Goal找出 AUM 下跌主因
Observe读取 KPI 与口径
Decide选择下钻维度
Act调用 SQL / Python
Validate核对加总与阈值
Deliver写入 Dashboard Insight

适合 Agent 的任务

  • 步骤多且会根据中间结果分支AUM 下跌后，需要判断先查客户流失还是产品重分类。
  • 需要跨系统找证据并整合从数仓取数、从指标库找定义、从报告库找历史解释。
  • 有重复频率，也有一定判断空间每月都做 MBR，但异常指标和下钻路径每次不同。

不必做 Agent 的任务

  • 一次性、低风险、一步完成只需把一段中文翻成英文，普通 Chat 足够。
  • 完全固定且可用代码精确表达每天把 CSV 移到归档目录，用普通脚本更稳定。
  • 没有明确输入输出或责任边界“帮我提升整个 MI”太宽，应先收敛为“检查 12 个 KPI 的环比异常”。
判断标准：是否需要“根据环境反馈持续决定下一步”。不是所有自动化都要 Agent 化；确定性步骤继续交给 SQL、规则与 Workflow。
03 / AGENT ANATOMY

一个完整 Agent 到底由什么组成

把 Agent 想成一个新入职但速度很快的分析师：需要岗位说明、工具权限、业务知识、工作流程和质量管理。

Agent 全景

Brain｜大脑

模型 + Prompt + 推理策略，负责理解目标和选择下一步。

例：看到 NNM 下降，先判断是流入减少还是流出增加。
AgentGoal + Context
+ Reasoning + Action
+ Validation

Hands｜双手

Tools 与 MCP，让 Agent 能查询、计算、生成和提交。

例：调用 SQL 查数、Python 做贡献度分析、写入 Dashboard。

Knowledge｜知识

指标定义、数据字典、Taxonomy、业务规则和历史案例。

例：知道 CASA 包含 CA 与 SA，但不包含 TD。

Workflow｜工作法

Skill 与 Harness 规定步骤、路由、状态、重试和交接。

例：必须先通过数据质量检查，才允许生成结论。

Governance｜治理

Guardrail、Validation、Observability 与 Human Review。

例：金额对不上总账时停止发布，转交数据 Owner。
其他常被忽略、但生产环境必需的组件
  • Context / Knowledge：当前任务需要的业务信息。本次报告范围是 HK Retail，不包含 SME。
  • Memory / State：记录任务做到哪里和已确认的事实。已完成 12 个 KPI 中的 8 个，AUM 口径已由 Owner 确认。
  • Guardrail / Policy：定义不可做与必须停下的条件。不得输出客户级 PII；未经审批不能写生产表。
  • Observability：记录每一步输入、工具调用、耗时和结果。能回看 Agent 为什么选择按 Segment 下钻。
  • Human-in-the-loop：把高风险判断交还给人。“活动导致余额增长”属于因果判断，发布前需分析师确认。
04 / CORE DISTINCTIONS

Prompt、Skill、Tool、MCP、Taxonomy、Harness 有什么区别

同一个例子讲清楚：为 Retail Banking Monthly Business Review 解释本月 AUM 变化。

核心概念
概念一句话它解决什么问题在 MBR 中的例子最容易误解
Prompt给模型的执行指令与约束“这一次应该如何思考和输出？”要求比较 MoM / YoY / Target，异常超过阈值才下钻，并引用数据证据。例：输出必须包含 KPI、差异、贡献维度、证据链接和置信度。Prompt 不是 Agent；它像岗位说明书，但不能自己接数据库或管理重试。
Skill可复用的专业做法包“这一类任务通常怎么做？”“月报分析 Skill”包含数据 QA、变化分解、重要性判断、叙事模板和检查清单。例：先看总量，再按 Product / Segment / Channel 分解贡献。Skill 不等于 Tool；Skill 是“会怎么做”，Tool 是“用什么做”。
Tool可被调用的具体动作“Agent 能做什么？”执行 SQL、运行 Python、搜索报告、渲染图表、提交评论。例：run_sql(query) 返回按产品分组的 AUM 变化。有 Tool 不代表会正确使用；锤子不会告诉你哪里该钉钉子。
MCP让 Agent 以统一方式发现并调用外部能力的协议“不同系统怎样用一套接口接给 Agent？”数仓、报告目录、Data Dictionary 分别暴露成可发现的 MCP Tools / Resources。例：Agent 先 list_tools，再调用 get_metric_definition。MCP 不是数据库，也不是业务逻辑；它是“通用插座”，不是“电器”。
Taxonomy统一业务对象的分类、命名与关系“大家说的是不是同一个东西？”Deposit → CASA / TD；Investment → MF / Banca；Flow → External In / Out。例：所有 Agent 都知道 SA 属于 CASA，而不是 TD。Taxonomy 不只是标签表；还应包含层级、别名、映射和生效版本。
Harness把模型、Prompt、Skill、Tools 和治理真正跑起来的运行框架“怎样稳定、可追踪、可升级地完成任务？”加载上下文、路由 Tool、保存状态、失败重试、运行验证、人工审批、记录版本。例：SQL 超时重试一次；金额不平则停止并通知 Owner。Harness 不等于 Workflow 图；它是承载工作流的“运行与治理系统”。
Taxonomy统一 AUM / CASA 等语言
Skill规定月报怎么分析
Prompt交代本次目标与边界
Tool + MCP连接系统并执行动作
Harness编排、验证、记录、重试
一句话记忆：Prompt 是任务单，Skill 是 SOP，Tool 是工具，MCP 是通用插座，Taxonomy 是共同语言，Harness 是整条生产线。Agent 是它们组合后，围绕目标持续运行的系统。
05 / BEST FIT FOR DA

DA 最适合做哪些 Agent

不是从“模型能做什么”出发，而是从 DA 的高频瓶颈出发：找数、查口径、分析、解释、出报表、触发行动。

场景地图

DATA

Data Discovery Agent

根据业务问题寻找数据集、字段、Owner、血缘和已有报告。

例：问“有没有客户流失数据？”Agent 返回三张候选表、口径差异和对应 Dashboard。

展望：从“搜索目录”走向“基于语义和使用历史推荐最可信资产”。

DATA

SQL / Data Prep Agent

把已确认口径翻成查询与可复现数据集。

例：按统一 CASA 口径生成 Segment × Month 的汇总 SQL，并附测试。

展望：与语义层结合后，减少每个人重复写相似 SQL。

DATA

Data Quality Agent

做完整性、及时性、一致性、异常漂移和对账。

例：发现本月 TD 少 18%，先检查源表迟到而不是直接写成业务下跌。

展望：从被动告警走向自动定位上游节点与影响范围。

ANALYSIS

KPI Analysis Agent

计算 KPI 并比较 MoM、YoY、Target、Forecast。

例：AUM 环比 -2.1%，比目标低 1.4pp，按客户层级展示贡献。

展望：让每次分析自动遵循同一对比基线和 Materiality。

ANALYSIS

Root Cause / Driver Agent

做贡献分解、相关线索与可检验假设，不轻易声称因果。

例：下跌的 72% 来自 Affluent 客群 TD 到期，但“利率导致”仍标为待验证假设。

展望：连接实验和事件数据后，可自动建议验证方案。

ANALYSIS

Forecast / Scenario Agent

运行预测与情景参数，解释结果敏感性。

例：假设 TD 续存率提升 3pp，模拟季度末 Deposit 差异。

展望：从单一预测升级为“假设—结果—风险”的可交互决策支持。

INSIGHT

Dashboard Insight Agent

从 Dashboard 中发现重要变化，生成可追溯解释。

例：不是把所有红点都念一遍，而是只选对总 AUM 影响最大的三项。

展望：成为 Dashboard 上下文中的持续 Copilot，支持追问与下钻。

INSIGHT

Campaign / Journey Agent

分析触达、转化、渠道路径与客户旅程断点。

例：发现 App 申请在 KYC 步骤流失集中，并按设备版本定位。

展望：把分析结论直接连接到下一轮实验设计。

INSIGHT

Challenger Agent

专门找证据缺口、逻辑跳步、口径冲突与另一种解释。

例：质疑“活动带来增长”，指出同期自然季节性尚未排除。

展望：成为高风险结论的强制第二视角，而不是可选润色。

REPORT

Monthly Report Agent

把验证后的数字、图表和洞察组合成标准月报。

例：自动生成 MBR 初稿，每段话都链接到数据快照和计算版本。

展望：同一事实层自动适配管理层、产品团队和执行团队版本。

REPORT

Executive Summary Agent

按受众和决策需求压缩信息，而不是简单缩写。

例：给管理层只保留“发生什么、影响多大、建议做什么”。

展望：基于角色权限和关注点生成个性化但事实一致的摘要。

FOUNDATION

Metadata / Dictionary Agent

维护指标定义、字段说明、Owner、变更和使用方式。

例：回答“Active Client 是 30 天还是 90 天口径？”并指向批准版本。

展望：自动从代码与使用记录发现“文档和实际不一致”。

优先级建议

先做 Data Discovery、Data Quality、Dashboard Insight / Monthly Report：频率高、边界清楚、容易定义 Golden Set。不要一开始做“万能 DA Agent”。

例：先覆盖一个 Retail Dashboard 的 12 个核心 KPI，跑通后再扩到其他产品域。
06 / BUILD THE RIGHT AGENT

怎么建好一个 Agent：不要先写 Prompt

先把任务当成一个可运营的分析产品设计，再决定哪些步骤由规则、代码、LLM 或人工完成。

设计方法

Business Goal｜业务目标

说明要改善的决策或结果，而不是“做一个 Agent”。

目标是把 MBR 初稿准备时间从 2 天降到半天，同时不降低数字准确率。

Input Contract｜输入契约

定义来源、粒度、时间范围、必须字段、版本和缺失处理。

输入是已关账的月度快照；若 freshness 超过 36 小时则禁止生成结论。

Output Contract｜输出契约

定义格式、字段、证据、受众和交付位置。

每条 Insight 必须含 KPI、变化值、最大贡献项、证据链接、置信度和 Owner。

Break into Steps｜拆解任务

把“分析一下”拆成可验证的中间产物。

QA → KPI → 异常检测 → 下钻 → 归因线索 → 排序 → 叙事 → 审核。

Decide Tool vs LLM｜分配执行者

精确计算交给代码；模糊理解和表达交给 LLM；高风险判断交给人。

环比由 SQL 计算，结论排序由规则 + LLM，因果声明由分析师批准。

Knowledge & Taxonomy｜准备知识

提供指标口径、层级、别名、阈值和历史规则。

AUM = Deposit + Investment；“Wealth”是展示别名，不可另算一套口径。

Validation｜定义验收

在开发前写出什么叫“对”，并准备 Golden Set。

12 个 KPI 数值 100% 对齐，重要问题召回率 ≥ 90%，无证据结论为 0。

Failure Handling｜设计失败

明确重试、降级、停止和转人工，不让 Agent “硬编过去”。

找不到 Target 时输出“Target unavailable”，继续做 MoM，但不生成 Target 比较。

Prompt + Test + Iterate｜最后才写 Prompt

把上述设计写成执行契约，跑回归测试并做版本管理。

Prompt v3 提高了异常召回，但误报上升；保留 v2 并调 Materiality 后再发布。
先设计 Workflow，再写 Prompt。如果没有输入、输出、验证与失败路径，再长的 Prompt 也只是一次性演示。
07 / PROMPT CONTRACT

好的 Agent Prompt 是一份“执行契约”

它不是靠语气“哄模型聪明一点”，而是减少歧义，明确边界、证据标准和不知道时怎么办。

执行契约

1. Role

你是谁、为谁工作。

例：你是 Retail MI 分析 Copilot，为 DA 分析师准备可审阅初稿。

2. Objective

最终要完成什么。

例：识别本月对 AUM 影响最大的可解释变化。

3. Business Context

范围、受众、时间与决策。

例：范围仅 HK Retail，受众是月度业务评审会。

4. Input Contract

允许使用哪些输入。

例：只使用已批准 KPI 快照与报告目录，不读取客户 PII。

5. Definitions

关键口径与阈值。

例：Material = 变化超过 1% 且金额超过 10M。

6. Task Steps

必须按什么顺序推进。

例：先 QA，再比较，再下钻；QA 未过不得写结论。

7. Tool Policy

什么时候调用什么工具。

例：所有金额由 SQL Tool 计算，禁止模型心算。

8. Reasoning Rules

判断时必须遵守的原则。

例：贡献度可以陈述，因果关系必须有额外证据。

9. Guardrails

哪些事情不能做。

例：不展示少于 10 人的小客群，不写入生产表。

10. Validation

输出前逐项检查。

例：分项贡献之和与总变化误差不得超过 0.1%。

11. Output Schema

机器和人都能稳定消费的格式。

例：JSON 字段固定为 metric、delta、driver、evidence、confidence。

12. Abstention + Examples

不知道时如何停，以及正反例。

例：证据不足就写“待验证假设”，并给出下一步查询。
差 Prompt
帮我分析这个月 Dashboard，有什么 insight？

问题：没有范围、口径、比较基线、阈值、证据、输出结构和失败规则。

好 Prompt 的核心片段
objective: 识别本月最重要的 3 个变化 compare: MoM, YoY, Target materiality: abs(pct_change) > 1% and abs(delta) > 10M rules: - 数值只来自 KPI tool - 相关不表述为因果 - 每条结论必须有 evidence_id if_unknown: 标记 unavailable，不猜测
08 / HARNESS

Harness：决定 Agent 能不能长期稳定地做

Prompt 决定“会不会做”；Harness 决定“能不能每天、每月、换人以后仍然稳定地做”。

生产化基础

Orchestration

决定步骤、依赖和多 Agent 交接。
例：QA Agent 通过后才启动 Insight Agent。

Context Loading

按任务装载最少必要知识。
例：只加载 Retail 的指标定义，避免混入 SME 口径。

Tool Routing

权限、参数校验、超时和限流。
例：生产查询只允许只读账户与批准数据集。

State & Retry

保存进度，针对可恢复错误重试。
例：第 7 个 KPI 超时，只重跑该节点，不重做全部。

Validation & Review

规则测试、Challenger 和人工关口。
例：数值一致但因果语句未审批，仍不可发布。

Logging & Version

记录模型、Prompt、数据、工具和输出版本。
例：三个月后仍能复现当时那条 AUM 结论。
生产 Harness 还需要管理哪些内容？
  • 成本与延迟简单分类用小模型，复杂解释才用强模型。
  • 发布与回滚Prompt v4 误报增加，可立即回滚 v3。
  • Run Manifest保存 data_snapshot_id、prompt_version、tool_version、reviewer。
  • 权限与审计不同用户只能查询自己有权限的数据域。
09 / TAXONOMY & SEMANTIC LAYER

DA Agent 需要一套共同的业务语言

如果概念不统一，Agent 越多，错误传播越快。Taxonomy 定义“有什么”；Semantic Layer 进一步定义“怎么算、从哪取、如何聚合”。

共同语言

Deposit

  • CASACurrent Account + Savings Account。
  • TDTime Deposit，按到期日和币种继续细分。
  • SD必须明确在本机构归 Deposit 还是 Investment。

Investment

  • MFMutual Fund，可按风险级别分类。
  • QDII跨境投资额度类产品。
  • Banca保险类产品，不应混入 Deposit。

Flow

  • External In外部资金转入，影响 NNM。
  • External Out外部资金转出，影响 NNM。
  • Internal TransferTD 转 MF 只改变产品结构，不应计入整体 NNM。

11 / DEEP DIVE CASE

重点案例：Dashboard Design Agent

让使用者只需提供一张输入表，再用配置说明“哪个模块展示什么、使用哪个字段”，Agent 就能生成风格统一、可继续修改的 WebApp Dashboard。

核心案例

现在的 MI 困境

  • 每个人都有很多 Reports，可能完全重复，也可能只重复一部分A、B 两份 Report 都有 AUM 趋势，但一个多了 Segment，另一个多了 Product。
  • 每个人再用 AI Coding 各自做 Dashboard同一张输入表最后变成三套不同代码，后续都要分别维护。
  • 页面风格和聊天界面越来越不一致A 的页面有筛选器，B 没有；C 的 Copilot 不知道当前选中了哪个月份。
  • 修改一个字段，经常要重新和 AI 解释整套需求只是把趋势图从 Balance 换成 NNM，也可能重新生成大量代码。

想做的 Agent

  • 大家共用一个 Dashboard Design Agent不用每个人重新写 React、图表和聊天框。
  • 使用者只准备“输入表 + 配置”上传 mi_monthly.xlsx，再选择 Month、Segment、AUM 等字段。
  • 配置决定每个模块展示什么KPI 卡片用 AUM 字段，趋势图用 Month + AUM，柱状图用 Product + AUM。
  • Agent 自动生成可运行的 WebApp生成页面、筛选器、图表、数据绑定和统一 Copilot。
目标不是让 Agent 每次“自由发挥”写一个新网站。目标是建立一个稳定的 Dashboard 模板，让差异只存在于输入表和配置中。

用户实际只走六步

① 上传输入表CSV / Excel / 数据视图
② Agent 读字段识别日期、类别、数值
③ 填 Dashboard 配置模块 + 字段 + 展示方式
④ 自动检查字段、类型、聚合是否合理
⑤ 生成 WebApp页面、图表、筛选器、Copilot
⑥ 预览并修改改配置即可重新生成

Input Table

使用者自己的 MI 数据。
例：Month、Segment、Product、AUM、Target。

Config

说明页面有哪些模块、每个模块绑定哪些字段。
例：趋势图：x=Month，y=AUM。

Component Library

预先做好的 KPI、折线图、柱状图、表格和筛选器。
例：所有人使用同一套 line_chart。

Design Agent

读取字段与配置，组合组件并生成代码。
例：发现 AUM 是数值字段，允许 sum 与 average。

WebApp Dashboard

统一布局、样式、数据绑定和响应式页面。
例：电脑和大屏都能正常显示。

Shared Copilot

自动获得当前页面、模块与筛选条件。
例：用户选 Affluent 后，Copilot 只解释 Affluent。

Dashboard 怎么“串起来”？

所有模块绑定同一份数据和同一个筛选状态。Month、Segment 等全局筛选器变化后，KPI、趋势图、柱状图和明细表一起刷新；Copilot 也读取同一份筛选状态。

例：点击 Segment = Affluent 后，AUM 卡片、月度趋势、产品分布和聊天回答同时切换到 Affluent。

使用者不需要写前端代码，只要说明：输入表在哪里、全局筛选器用什么字段、每个模块是什么类型、绑定什么字段、怎样聚合。

使用者必须提供

字段检查、布局、组件代码、数据绑定、颜色、格式和响应式页面。

配置错误时

先给出人能看懂的提示，不生成一个坏页面。

例：“Line Chart 的 x 需要日期或类别；当前字段 Amount 不合适。”

Copilot 的职责：帮用户完成配置，不是替用户重新写一套网站

Copilot 需要知道

  • 输入表有哪些字段和字段类型Month 是日期，AUM 是数值，Segment 是类别。
  • 平台支持哪些模块只允许 kpi_card、line_chart、bar_chart、table 等受测组件。
  • 当前 Dashboard 配置知道趋势图现在绑定的是 Month + AUM。
  • 当前页面的筛选状态用户正在看 2026-09 与 Affluent。

Copilot 可以帮助

  • 根据自然语言生成配置“上面放四张 KPI 卡，下面放 AUM 趋势”。
  • 修改某个模块“把 Product 柱状图改成横向，并显示 Top 10”。
  • 发现字段不匹配用户写 Revenue，但输入表只有 Income，Copilot 先询问而不是猜。
  • 解释当前 Dashboard“这张图展示什么？”根据模块配置和当前筛选回答。
# Dashboard Design Copilot：核心 Prompt Role: 你是 Dashboard Design Copilot，帮助用户把输入表转换为 Dashboard 配置。 Inputs: table_schema、current_config、component_library、user_request。 Workflow: 1. 先检查用户提到的字段是否存在、类型是否合适。 2. 把用户需求映射为受支持的 Dashboard 模块。 3. 只新增或修改必要的配置，不重写无关部分。 4. 调用 validate_config；通过后再调用 generate_webapp。 5. 返回修改说明、配置草稿、校验结果和预览入口。 Rules: - 不创造输入表里不存在的字段。 - 不生成组件库之外的新组件；无法满足时明确说明。 - 数值字段必须明确 aggregation；日期字段必须明确 grain。 - 不确定字段含义时先询问用户。 Tools: inspect_table、list_components、validate_config、generate_webapp、preview_dashboard Output: config_patch + warnings + preview + change_summary

一次真实对话会很简单

用户：“用这张表做一个 Dashboard：上面显示 AUM、NNM、Target 三张卡；中间画 AUM 月度趋势；下面按 Product 展示 AUM。”
Copilot：读取字段 → 确认 AUM / NNM / Target / Month / Product 都存在 → 生成配置 → 校验 → 输出 WebApp 预览。

后续修改：用户只需说“趋势图按 Segment 分颜色”，Copilot 只给该模块增加 color: Segment。

真正需要完成的，是一套可复用的 Dashboard 生成产品

1. Input Adapter

读取 CSV、Excel 或批准的数据视图，并识别字段类型。

交付：上传表后展示字段名、类型和样例值。

2. Config Schema

定义筛选器、模块、字段、聚合、布局和主题可以怎样填写。

交付：dashboard.schema.json + 表单界面。

3. Component Library

预制 KPI、折线图、柱状图、饼图、表格和筛选器。

交付：首版 6 个稳定组件。

4. WebApp Generator

把配置转换成页面、数据绑定、交互和可运行代码。

交付：一键生成并预览 WebApp。

5. Design Copilot

读取表结构，通过对话新增或修改配置。

交付：自然语言 → config patch → 校验 → 预览。

6. Validator

检查字段是否存在、类型是否合理、模块能否渲染。

交付：错误定位到具体模块和字段。

建议的第一个 POC
只支持一种标准输入表、6 个模块、3 类全局筛选器和一个统一主题。使用者可以上传表、填写配置、生成 WebApp，并通过 Copilot 修改模块。例如先用 Retail MI 表，生成 KPI 卡片、AUM 趋势、产品分布和明细表。
第一版暂时不要做什么
不要支持任意前端组件，不要让 Agent 自由重写整套代码，不要一开始兼容所有 Report 格式，也不要把复杂洞察分析混进 Dashboard Design Agent。这个 Agent 第一阶段只负责“把表和配置稳定地变成 Dashboard”。
