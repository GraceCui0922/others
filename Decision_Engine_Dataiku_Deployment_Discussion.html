Decision Engine · Deployment Architecture Discussion

Dataiku-native deployment vs. Python Server + Dataiku LLM Mesh

Purpose: provide enough architecture context for a Dataiku expert to recommend the simplest and most governable deployment model. The business logic is already prototyped locally; the open question is where runtime, validation UI and operating controls should live.
Discussion objective. We are not asking Dataiku to redesign the Decision Engine. We want to determine whether to (A) decompose and deploy it natively inside Dataiku, or (B) keep it as a self-contained Python application on a corporate Python Server and call Dataiku LLM Mesh remotely, while preserving governance, permissions, validation interfaces and auditability.

2Current implementation status & pain points

What already works locally

  • Large Python agent framework already runs with local mock datasets.
  • Prompts, Python logic, orchestration and validation logic can be debugged together.
  • Local UI / dashboard can be developed as one integrated application.
  • Target design is to replace mock datasets with production datasets without rewriting core logic.

Why Dataiku migration may become operationally heavy

  • Python package/code may need to move into Project Libraries / Code Environment.
  • Execution logic may need to be split into multiple Flow recipes.
  • Datasets, configs, prompts and artifacts may live in different Dataiku components.
  • Validation and review may require separate datasets, dashboards or web interfaces.
  • Frequent local code/prompt changes may create manual deployment and synchronisation work.
3Two deployment patterns to evaluate
Area Option A · Dataiku-native Option B · Python Server + Dataiku LLM Mesh
Runtime DATAIKU
Python libraries + recipes/notebooks/scenarios inside DSS.		 PYTHON SERVER
Entire application runs as one Python service/app.
LLM access Directly through Dataiku LLM Mesh from DSS runtime. Python Server remotely calls Dataiku LLM Mesh, subject to API/network/auth feasibility.
Production data Native Dataiku datasets/connections and Flow lineage. Need a governed way for Python Server to read production data or receive prepared datasets.
UI / validation Datasets + charts + dashboards / possible web UI; may be split across Dataiku components. One integrated custom dashboard/UI can be built and tested locally, then deployed with the server.
Iteration speed Potentially slower if every prompt/code/UI change requires several Dataiku assets to be updated. Potentially faster for a complex agent application because code + UI + harness remain one deployable unit.
Governance / permission STRONG
Data, LLM access, project permissions, lineage and execution remain in the Dataiku governance boundary.		 TO CONFIRM
Requires governance for server access, service identity, secrets, network, audit and Dataiku API permissions.
Operating model More Dataiku-native and easier for platform governance/support. More software-engineering-native and potentially easier for rapid agent/UI evolution.
4Non-negotiable requirements

Governance & security

  • Production data access must remain controlled and auditable.
  • LLM calls must use the approved Dataiku LLM Mesh rather than unmanaged provider keys.
  • Node-level permissions, run logs and version traceability are required.

Research / validation usability

  • Every node needs a visible validation interface and review harness.
  • Users must be able to inspect outputs, failures, distributions and review queues.
  • Prompt / mapping / parameter changes need clear edit points and fast re-run / comparison.
5Questions for the Dataiku expert

We would like your recommendation on the deployment boundary.

  1. Can a corporate Python Server call Dataiku LLM Mesh reliably through an approved API? What authentication, network and service-account model would be required?
  2. If we stay Dataiku-native, what is the cleanest pattern for a large multi-node Python agent framework: Project Library + a small number of recipes, or many node-level recipes?
  3. For node-by-node validation, human review and editable controls, should we use Dataiku dashboards, webapps, datasets, scenarios, or another pattern?
  4. How much manual deployment/synchronisation is required when code, prompts and configs are iterated frequently?
  5. Can we establish a practical local development → Git/CI → Dataiku deployment workflow so Dataiku does not become a manual copy/paste environment?
  6. From a governance and support perspective, would you recommend Dataiku-native, Python Server, or a hybrid where Dataiku owns data/LLM/governance and Python Server owns the application runtime/UI?
